# 简体中文审校规范

## 质量标准

- **信**：以当前官方英文为语义基准，核对主体、对象、否定、范围、前提、数量与操作后果。先从英文和上下文理解含义；官方简中与历史译文在需要时查阅并核实。
- **达**：根据界面上下文组织中文，保留完整信息。按钮使用清楚的动作，标题使用稳定的名称，提示说明条件和结果。
- **雅**：简洁、自然、克制，不增添宣传语、夸张语气和原文没有的信息。统一称呼“你”，使用中文标点和省略号“…”；URL、代码与协议字面量保持原样。
- **一致性**：各平台共用下表，同一功能内标题、按钮、说明保持一致。上下文导致同一英文需要不同译法时，在审校备注里说明具体原因。

## 审校与验收

1. 对新增、英文变化和定向修订条目，先根据当前英文、旧英文变化与功能上下文确定含义；按相关 key 查阅成对的旧英文与精修译文，核对术语和表达。跨平台复用须核对用途、参数角色与格式；适用时直接采用，其余内容改写或新译。相同英文可合并审阅，各 key 的语境差异须分别处理。官方简中和社区包只用于具体疑点的交叉核对。
2. 初译完成后，单独再逐条对照英文复核语义与格式，再统一同功能文案和复数分支，复查跨平台术语。全量风格修改须先列出命中条目、核对上下文，不能盲目替换同形词。
3. 保留所有占位符、参数角色、链接目标、富文本结构和必要换行。无编号参数保持原有次序。
4. 结构校验通过后仍须检查译文语义；机器校验不判断“信、达、雅”。
5. 在 `review.md` 记录实际复核范围、问题处理、术语决策和上下文证据。涉及含义的未决问题解决前不宣告完成。保存变更报告、下载来源与校验结果，最终文件供人工上传至对应平台。
6. 原文未变且准确自然的译文稳定复用；发现错误、功能语境变化或术语冲突时定向审校。模型升级继续遵循同一标准，不能仅凭“模型更强”认定已有译文需要改写或新译文已经可靠。

## 容易通过结构校验的语义错误

以下情况在四端对照审校中实际出现过，机器校验通过后仍须人工核对：

| 核对点 | 实际问题与处理方法 |
|---|---|
| 参数的完整内容 | 参数可能已包含数量、单位、百分号或“每天”。例如邀请链接参数已是“3 个现有邀请链接”，礼物属性参数已是百分比。查看调用处及生成参数的复数词条，再决定外层句子是否需要单位。 |
| 参数角色与次序 | `Gift.Convert.Period.Text` 的第一个参数是赠礼人；把 `from` 译为兑换来源会改变含义。无编号参数须按调用顺序对应，不能只比较占位符集合。 |
| 主体、否定与条件 | 隐私设置须分清谁向谁公开状态、例外是否受上方设置影响；离线删除须保留“一次也没有上线”的条件。按完整条件句复核，不能只检查关键词。 |
| 动作与状态 | `Complete Payment` 是“完成付款”；静音按钮须区分通话静音与关闭通知。查看按钮调用或界面用途，避免把待执行动作写成已完成状态。 |
| 复数各分支 | 同一组的中文有效分支可能保留旧译，其他分支已经正确。复核整组，并单独确认 iOS `_any`、其他平台 `other` 分支；全分支结构数量与实际发布词条数量分别记录。 |
| 显示格式 | 孤立的 `%`、粗体范围、链接目标、真实换行与字面 `\n` 都可能影响显示或含义。对照解析后的字符串与构建后再解析的结果，不能只看 JSON 或 `.strings` 的转义外观。 |
| 同词不同用途 | `Model` 在礼物中是“款式”；`Private Chat` 按普通私聊语境处理，`Secret Chat` 才是“私密聊天”。术语替换前列出命中 key，逐项确认功能。 |

相同英文可用于聚合跨端候选，但另一端的译文仍须按当前英文、界面用途和参数角色核实。源码证据应保留仓库、提交版本、文件和调用位置，方便以后复查。

## 审校范围与结果留存

- 对已有全量译文做定向审校时，优先核对跨端差异、长条件说明、隐私和付款提示、按钮动作、参数及术语冲突；准确自然的表达继续保留。
- 修改前归档当前主文件，保存逐 key 的英文、原译、新译、原因和上下文依据；初稿完成后另做一遍语义复核，最终只应用确认的清单。
- `review.md` 分别写明逐条语义复核范围、自动扫描范围、结构校验范围和客户端验收状态。按同一英文合并审阅的组数、各平台 key 数、含复数的修订数与中文有效词条数分别统计，不能互相替代。
- 本地成品验证与线上发布验证分别留存；上传后的生效情况按 [上传验收方法](05-troubleshooting.md#验收与记录) 重新导出核对。
